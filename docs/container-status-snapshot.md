# 상태 조회 중복 실행 억제

REST 목록, WebSocket 첫 화면 및 주기 방송은 같은 DockerService 인스턴스의 조회를
공유한다. 동시에 들어온 요청은 한 번의 전체 조회 결과를 받고, 오류가 없는 결과만
완료 시점부터 monotonic 기준 2초 동안 재사용한다. 반환값은 매번 복사하여 호출자의
수정이 다른 화면에 전파되지 않는다. 예외 및 error/offline/unreachable/down 관측은
캐시하지 않으며 이미 기다리던 요청에는 같은 실패가 전달된다.
로컬 exited/created/not_created 관측은 캐시할 수 있다. 원격 down은 HTTP 실패 응답,
unreachable은 전송 실패로 구분되며, 하나라도 있으면 전체 캐시를 우회한다.
이 상태가 지속되면 캐시 적용률은 0일 수 있고 동시 실행 합치기 효과만 남는다.
현재 계측에는 상태별 분포가 없어 실제 캐시 적용률은 미측정이다.

Docker 시작·정지·재시작, 설정 수정·초기화와 Compose ensure, pinned rebuild,
공용 Dagster converge의 전후 epoch를 바꾼다. 실패한 변경도 부분 효과가 있을 수
있으므로 무효화한다. 작업 중 조회는 공유하지만 캐시하지 않는다. 변경을 가로지른
조회는 다시 읽어 변경 후 요청에 이전 결과를 돌려주지 않는다.
스레드의 공유 Future는 asyncio 요청 취소와 연결하지 않으므로 WebSocket 종료나
대기 취소가 다른 요청의 조회를 취소하지 않는다.

캐시는 관측 전용이다. 권한 판정, 변경 대상 식별, Docker 변경 검증에는 쓰지 않는다.
외부 Docker 명령이나 다른 프로세스의 변경은 이 프로세스의 epoch를 바꾸지 않으므로
정상 관측 캐시의 최대 2초 지연이 있다. 별도 프로세스 사이의 공유 캐시는 없다.
Docker 점검이나 원격 HTTP 예산, 프런트엔드 재연결 및 테스트 제한 시간은 늘리지 않는다.
오래 걸리는 Docker 호출 자체에 새 종료 보장을 제공하지 않는다.

## 근거와 검증 범위

이전 제품의 단일 읽기 전용 계측에서 전체 조회 wall 1.26655초 / process CPU
1.00576초였다. Docker inspect 38회와 image inspect 15회, 원격 관측 1묶음이
포함되었다. 별도 프로세스의 최초 import 6.686초는 운영 요청 비용이 아니다.
과거 UI의 15초 제한 초과 원인은 이 표본에서 재현되지 않아 미확정이다.
이 변경은 중복 비용을 줄이며, 운영 CPU 감소나 지연 해결을 이미 실측했다고 주장하지 않는다.

반례는 성공 캐시의 완료 시점/복사, 오류 재시도, 공유 예외, 변경 중 epoch 경합,
실패한 변경의 무효화, 대기 취소 격리와 실제 REST handler/WS 방송 함수 공유를 검사한다.
기존 Docker 설정 회귀 포함 초기 124개가 통과했다. 이후 원격 오류 상태 반례 두 개를
추가한 최종 10개 반례는 0.42초에 통과했다.

첫 전체 로컬 검사는 3217 PASS / 5 FAIL / 3 SKIP (1239.89초)였다. 실제 Docker
통합의 기존 테스트가 location 상한 10보다 전역 상한이 커야 한다고 가정한 1건,
생성자를 우회한 remote fixture가 새 캐시 필드를 초기화하지 않은 4건이었다.
첫 CI도 같은 remote fixture 4건 실패, 3182 PASS / 39 SKIP (578.61초)였다.
제품 코드는 유지하고 fixture는 실제 생성자를 사용한다. 전역 포화 시 두 location이
모두 대기하는 검증을 추가했으며, location별 검증과 잘못된 tag 대조군에만 격리
instance의 전역 여유를 준다. 운영 전역 상한 2는 바꾸지 않는다.
수정 후 집중 통합 검사와 새 CI는 진행 중이다. 첫 전체 검사를 PASS로 바꾸어
기록하지 않는다. 운영 배포 및 공개 UI 회귀는 아직 수행하지 않았다.
